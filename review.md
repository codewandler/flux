# Verdict
The immediate code-level risks are a credential leak vector from internal tool results bypassing redaction and a secrets-grant bypass in plugin handshakes. The voice driver contains dead logic that misrepresents control flow. Architectural coupling — `flux-agent`’s wide fan-out, layer blurring in `flux-tools` and the plugin workspace dependency model — raises maintenance risk over time. Fixing the security gaps and dead code should be prioritised; the layering concerns require a dependency audit to confirm.

## High
1. **`crates/flux-plugin/src/lib.rs:OperationSpec.internal`** — *Credential leakage via internal‑op results*  
   The `internal: true` flag hides the operation from tool listings but does **not** redact the result before it enters the model-visible context. If a host fails to wire a `SecretSink`, raw credential material can leak. **Severity: High** — **lenses: Security**

2. **`flux-agent` (workspace-wide)** — *Hub with excessive fan‑out*  
   `flux-agent` appears to depend on peers across the language, execution, and policy layers (8+ crates). This makes it the most likely integration bottleneck and a magnet for layering violations. **Severity: High** (confidence medium — inferred from naming; requires a `cargo tree` audit to confirm. **lenses: Architecture**)

## Medium
3. **`crates/flux-plugin/src/lib.rs:resolve_handshake_secret`** — *Deliberate secrets grant bypass*  
   The host reads secret env keys for the plugin’s auth handshake without checking the plugin’s `secrets` grant. The plugin binary can observe and exfiltrate the secret through the protocol, despite the code comment justifying the bypass. **Severity: Medium** — **lenses: Security**

4. **`crates/flux-plugin/src/lib.rs:serve()`** — *No backpressure or integrity on plugin stdio*  
   On a malformed frame the loop silently `continue`s without error, counter, or abort threshold. Concurrent or garbled frames can desynchronise the request/response pairing (only a counter correlates them). No frame timeout or size checks are enforced. **Severity: Medium** — **lenses: Security**

5. **`crates/flux-flow/src/voice/driver.rs:58‑61`** — *Dead mutable booleans*  
   `response_active`, `response_done`, `response_had_tools` are declared `mut` but never read. A reader expects them to gate response creation based on the “debounce” comment, but they are never used. **Severity: Medium** — **lenses: Clarity**

6. **`crates/flux-flow/src/voice/driver.rs:61`** — *`tools_in_flight` counter never incremented*  
   The counter is meant to track in‑flight tool calls to enforce one response per batch, but it is only decremented (`.saturating_sub(1)`) and never incremented, so it stays at 0 forever. The invariant is broken. **Severity: Medium** — **lenses: Clarity**

7. **`crates/flux-flow/src/voice/driver.rs:56‑57`** — *Over‑promising comment*  
   The block comment promises debounce semantics (“one `create_response` per response, after *all* of its tool calls resolve — never one‑per‑call”) but the code does not implement that behavior, actively misleading maintainers. **Severity: Medium** — **lenses: Clarity**

8. **`crates/flux-tools`** — *Layer ambiguity*  
   The crate sits at the execution layer but carries low‑level primitives that should belong to the foundation layer (`flux-core` / `flux-spec`), making its responsibility unclear. **Severity: Medium** — **lenses: Architecture**

9. **`flux-interpreter` (missing crate manifest)** — *Possible language‑runtime conflation*  
   If the interpreter lives inside `flux-lang` as a module, that crate owns both AST/compiler and runtime execution, violating the layer separation rule. **Severity: Medium** — **lenses: Architecture**

10. **`flux-flow`** — *Duplicate dispatch logic risk*  
   Flow‑level constructs (loops, retries) are likely modelled both here and in `flux-runtime`, creating a source of drift. **Severity: Medium** — **lenses: Architecture**

11. **Plugin workspace (`plugins/`)** — *Cross‑workspace coupling ambiguity*  
   The two workspaces’ dependency relationship (path vs. version) is not governed by the layering table, potentially allowing version‑skew between main and plugins. **Severity: Medium** — **lenses: Architecture**

## Low
